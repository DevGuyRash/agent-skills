# Trigger Evidence

Trigger evidence observes whether a supported host retrieves the skill for intended work and leaves adjacent work to its proper owner. Static metadata inspection can suggest a boundary; it cannot prove activation.

Identify the description and installed copy the host actually routes against. Repository text that has not reached the active cache does not explain live behavior. Include sibling metadata only when it can materially compete for the same work.

Use natural requests around the consequential boundary rather than a term inventory. Evidence may include clear intended work, implicit intended work, nearby work owned elsewhere, and genuinely ambiguous work, but no fixed case list proves a semantic boundary. Vary phrasing or repeat an observation only when nondeterminism or dependence on one wording could change the conclusion.

Retain the exact request, surfaced skill, host and version, intended owner, and uncertainty. Repeated misses can support a metadata repair; repeated theft from an adjacent capability can support a narrower boundary. Express the discriminating intent rather than enumerating every phrase that happened to work.

Explicit invocation establishes that a selected skill can load. It does not establish implicit routing. Likewise, with/without task comparisons establish contribution after selection, not whether the host would select the skill unaided.

If live activation cannot be observed, describe retrieval as unverified. A keyword checker, static fixture corpus, or a clean description validator does not close that gap.
